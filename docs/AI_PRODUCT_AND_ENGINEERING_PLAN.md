# Kris AI 产品与工程方案

更新时间：2026-09-10

## 1. 产品定位

Kris 是“日常健康与专业训练中枢”。AI 不是单独的聊天产品，也不替代健康算法，而是把用户意图和本地健康结论转成更容易理解、审核和执行的建议。

核心分工：

- 本地算法：HealthKit 聚合、准备度、安全门槛、负荷、动作进阶和离线可用性。
- AI 助手：自然语言理解、健康趋势解释、训练候选计划和周期总结。
- 审核发布：结构校验、本地规则复核、差异展示和用户明确确认。

产品在 DeepSeek 无网络、余额不足、限流或服务异常时，仍可查看健康数据、完成训练、记录组次和运行本地规则。

## 2. 用户价值与首批场景

### P0：训练候选计划

用户输入当天目标、可用时间、器械、偏好和身体反馈。App 只发送最小化聚合上下文，DeepSeek 返回结构化候选计划。候选计划必须通过本地校验，并在训练页由用户确认后才发布。

这个场景优先级最高，因为它直接替代开发阶段“外部教练生成后再导入”的断点，同时复用现有 `TrainingPlanCandidate.v1`。

### P1：健康周报解释

把 7/14/42 日趋势、本地数据质量和训练负荷解释成三部分：发生了什么、证据是否充分、下周保持或调整什么。不得把单日体重、体脂或手表热量解释成长期变化。

### P1：自然语言记录

把用户输入的训练反馈解析成草稿字段，例如“提前结束、力量尚可、无肩肘腕不适”。用户核对后再保存，未提及的症状保持“未填写”。

### P2：可追问解释

允许用户围绕当前卡片追问“为什么”“哪些数据缺失”“如果今天不训练会怎样”。入口依附健康、趋势和计划卡片，不增加第六个 Tab，也不使用通用聊天首页。

## 3. 端到端架构

```text
HealthKit / 训练记录 / 用户输入
              |
              v
      iPhone 本地确定性引擎
      - 数据去重与质量门槛
      - 准备度与安全门槛
      - 负荷与动作进阶
              |
              v
        最小化上下文构造器
      - 不含样本 UUID / 设备 ID
      - 日期级或周期级聚合
      - 用户可预览发送范围
              |
              v
          Kris 服务端网关
      - App/设备鉴权、预算、限流
      - Provider 路由与密钥隔离
              |
              v
          DeepSeek Provider
      - 供应商结构化输出
      - 超时、错误分类与熔断
              |
              v
       Schema + 本地规则校验
              |
              v
       候选卡 -> 用户确认 -> 发布
```

供应商代码保持可替换。DeepSeek 是首个默认 Provider，但领域契约、候选状态和本地校验不依赖其私有类型。

## 4. 当前已落地的 AI 工程切片

- `AIRedactedPlanContext.v1`：只包含目标、可用时间、器械、准备度分级、本地规则结论、日期级训练摘要、当前计划摘要和数据缺口。
- `AIPlanResponse.v1`：固定候选计划 JSON 响应。
- Kris 网关客户端：临时 URLSession、45 秒请求超时、无 Cookie/缓存/供应商凭据存储、支持取消和明确错误状态。
- App 设备会话：每次请求从 Keychain 读取 Kris 短期会话令牌，并发送稳定的客户端请求 UUID；App 不保存 DeepSeek Key。
- 网关核心骨架：独立位于 `services/ai_gateway/`，包含严格契约、开发期 HMAC 会话、限流、幂等、Provider 接口和隐私审计。
- 网关 HTTP 入口：提供 `GET /healthz` 与 `POST /v1/ai/training-plan-candidates`，限制 64 KiB 请求体，默认返回 `no-store` 和 `nosniff`。
- 共享契约：`shared/schemas/` 已固定请求、响应和统一错误的 v1 JSON Schema。
- 供应商隔离：DeepSeek API Key 只进入服务端密钥管理，永不下发 App，用户不需要申请或填写。
- 结构化响应：App 只接受 `AIPlanResponse.v1`，空响应只重试一次；DeepSeek 的 JSON Output、提示词和模型路由由服务端实现。
- 本地校验：限制时长、动作数量、组数、次数、休息和重量范围；安全停止信号不能发布 AI 候选。
- 发布状态：供应商只返回结构化建议；App 只能写入 `awaiting_confirmation` 候选，不能直接调用当前计划保存路径。
- 设置页：只展示服务状态、发送范围与发布规则，不出现供应商、模型档位或 API Key 配置。
- 训练页：候选生成表单、发送范围预览、加载/取消/失败状态、候选审核与采用/放弃。
- 候选编辑：采用前可修改计划名称、目标、时长、动作、器械、重量、组次和休息；修改后重跑本地校验，仍不自动发布。

当前 App 已移除 BYOK 与 DeepSeek 直连。构建时未注入网关地址，或 Keychain 中没有 Kris 设备会话时，界面显示“服务准备中”；本地健康和训练能力不受影响。网关当前只允许确定性 Stub Provider，用于验证安全链路，不能声称真实模型调用已通过。

## 5. Kris 网关与 DeepSeek 接口基线

App 侧固定接口：

- `POST /v1/ai/training-plan-candidates`
- 请求：`KrisAIPlanRequest.v1`，仅含 `AIRedactedPlanContext.v1`
- 响应：`AIPlanResponse.v1`
- App 请求体不包含供应商名、模型名或供应商 API Key。
- 正式服务使用匿名 App 用户/设备会话鉴权，并结合 App Attest；不能把网关做成公开、无鉴权的模型转发器。

服务端 Provider 适配器按 DeepSeek 官方文档实现：

- Base URL：`https://api.deepseek.com`
- Chat Completions：`POST /chat/completions`
- 鉴权：Bearer API Key，仅存在服务端
- 结构化输出：`response_format.type = json_object`
- 官方 JSON Output 文档要求提示词中出现 JSON，并提示可能偶发空内容。
- 错误按 400/401/402/422/429/500/503 分类显示，不把所有问题都描述成“网络错误”。

官方模型路由和价格会变化，因此模型标识只属于服务端路由配置，不进入 App 设置或领域契约。发布前必须重新核对官方模型列表、定价和数据条款。

## 6. 隐私、安全与合规边界

### 默认最小化

发送：

- 用户本次主动输入；
- 准备度分级、置信度和安全门槛；
- 最近训练的日期级摘要；
- 当前计划与本地进阶结论；
- 数据缺口。

不发送：

- HealthKit 样本 UUID；
- 设备 ID、Apple Watch 标识或来源设备名称；
- 逐分钟心率、原始睡眠区间；
- 与当前任务无关的健康字段；
- Mac/SyncHealth 内部同步信息。

### 强制门槛

- 危险信号优先于模型建议。
- AI 不得把缺失数据写成“正常”。
- AI 不得自动加重、自动发布、代填症状或给医学诊断。
- 训练开始后锁定计划修订；新候选延迟到本次训练结束后采用。
- 模型原文不写入健康日志；只保存通过 schema 的结构化候选和必要的来源/版本。

### 对外测试前必须补齐

- 匿名用户/设备注册、短期 App 凭证与 App Attest 校验。
- 服务端密钥隔离、单用户预算、限流、熔断、审计和模型路由；日志不得写入原始健康上下文。
- 明确的隐私政策、用户数据导出/删除、供应商数据处理条款。
- 中国大陆健康数据、个人信息、跨境传输和未成年人场景的专项法律审查。

开发期 HMAC 会话和内存限流/幂等存储只能用于本机与 CI。生产环境配置当前会主动启动失败，直到 App Attest、可撤销服务端会话、共享限流/幂等存储和正式 Provider 全部实现，避免把测试骨架误部署为商用服务。

当前文档不构成合规结论，也不能对外宣称已经完成医疗器械或健康数据合规认证。

## 7. UX 与视觉原则

- 不增加 AI Tab；AI 入口附着在“设置、训练、健康解释、趋势总结”。
- 不使用机器人头像、闪光星星、大面积渐变或聊天气泡作为主视觉。
- 使用现有荧黄品牌色承载主操作，AI 来源使用系统蓝，本地规则通过使用系统绿，警告使用系统橙/红。
- 清楚区分“AI 建议”“本地规则已检查”“待你确认”。
- 生成过程不遮挡全屏，可取消；离开页面后任务取消，失败后保留用户输入。
- 触控区域至少 44pt；支持动态字体、VoiceOver、深浅色与减少动态效果。
- 所有专业判断使用自然文案，避免“智能洞察赋能”“不直接吃回”等模板化 AI 文案。

## 8. 质量与评估

### 离线与确定性测试

- 最小化 payload 不出现样本 UUID、设备 ID 或原始心率序列字段。
- JSON 缺字段、超时、空内容、非 JSON、超范围参数全部失败，不生成计划。
- 安全停止信号无法采用候选。
- AI 不能绕过 `awaiting_confirmation` 直接发布。
- 网关未配置或 DeepSeek 不可用时，本地 HealthKit、准备度和训练执行不受影响。
- App 二进制、Info.plist、UserDefaults、Keychain 和请求体均不出现供应商 API Key。

### 模型质量集

建立至少 50 个匿名黄金案例，覆盖：

- 无当前重量、器械占用、时间不足；
- 恢复信号低、数据缺失、训练间隔变化；
- 当前计划已存在、同日修订、跨日新计划；
- 腰骶或关节不适、危险症状；
- 力量、有氧、混合和低频训练用户。

核心指标：

- schema 通过率 ≥ 99%；
- 安全门槛召回率 100%；
- 首次候选采用率；
- 用户修改动作/组次/重量的比例；
- 生成中止率、P50/P95 延迟、单次成本；
- AI 不可用时主流程完成率。

## 9. 版本计划与工作安排

### AI-A0：端侧安全边界（当前轮）

- Provider-neutral 契约、Kris 网关客户端、最小化上下文。
- 设置与训练候选审核 UI。
- 单元测试、模拟器构建、无网关降级。
- 删除旧 BYOK Keychain 项和旧偏好，不向用户暴露供应商配置。

退出条件：App 侧安全边界、候选审核和无网关降级全部通过；关闭网络后 App 主流程照常工作。当前代码和自动化测试已满足，真机交互回归仍随下一安装包继续验收。

### AI-A0.5：接入前网关骨架（本轮完成）

- 严格请求/响应契约、64 KiB 上限和敏感 HealthKit 字段拒绝。
- Bearer 设备会话验证、固定窗口限流、请求幂等和内容冲突检测。
- Provider-neutral 接口与确定性 Stub Provider。
- 仅元数据审计，不保存健康上下文、用户备注或模型正文。
- App 使用构建期网关地址和 Keychain 中的 Kris 短期会话，不出现用户 API Key 设置。

退出条件：Stub HTTP 端到端、鉴权、敏感字段、限流、幂等和审计测试全部通过；生产模式在正式鉴权与 Provider 未实现时必须拒绝启动。

### AI-A1：受控网关闭环

- 网关实现设备注册、App Attest、短期且可撤销的会话令牌、共享限流、预算和请求追踪。
- DeepSeek Provider 适配器、结构校验、模型路由、超时、熔断与敏感日志清理。
- 部署环境使用 TLS、托管密钥和持久化幂等记录，不复用开发期 HMAC 签发器或内存状态。
- 部署开发环境并完成一次真机真实候选生成、编辑、确认和离线降级验收。

退出条件：真实生成一次候选，校验通过，用户确认后成为当前计划；供应商密钥未出现在客户端或日志。

### AI-A2：实用性完善

- [已实现] 用户可编辑候选动作、器械、重量、组次、次数和休息后再采用。
- 候选与当前计划差异视图。
- 后台/前台恢复、请求去重、失败重试策略和成本记录。
- 健康周报解释卡，不增加聊天首页。

退出条件：20 个内部案例中，候选无需大改或只做轻微修改的比例达到 80%。

### AI-A3：个性化闭环

- 训练反馈自然语言解析为待确认字段。
- 候选采用、修改、拒绝原因进入本地偏好模型。
- 周期目标、可训练日、可用器械和训练频率成为端侧用户档案。
- Prompt/规则/模型版本可回滚，模型升级先跑回归集。

退出条件：连续 4 周使用中，无静默加重、无症状误填、无重复发布。

### AI-A4：商用服务层

- 自有后端代理、匿名 App 用户、设备鉴权、预算和限流。
- Provider 路由、灰度、熔断和模型版本治理。
- 用户同意、数据导出/删除、隐私审计与运营看板。
- TestFlight 小规模内测，再决定订阅与公开发布。

退出条件：安全评审、隐私审查、成本压测、故障演练和 TestFlight 验收全部通过。

## 10. 当前非目标

- AI 自动控制 HealthKit 写入。
- AI 自动发布或自动加重。
- 医疗诊断、疾病风险评分或替代医生建议。
- 把 Mac companion、Obsidian 或 SyncHealth 重新变成 App 运行依赖。
- 为了“有 AI 感”而新增通用聊天、AI Tab、虚拟人或信息流。
